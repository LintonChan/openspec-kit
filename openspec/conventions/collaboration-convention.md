# 多 PM 协作规范

> 目的：多位 PM 往同一个 openspec 根里写需求时，如何做到互不踩踏、跨人依赖不失控。
> 本仓 `openspec/config.yaml` 已声明遵循本规范。

## 一、单根共享 还是 各开各的仓：判据是「共不共用底座」

新产品线来了，第一个问题是**进现有仓，还是起一个新仓**。判据只有一条：

| 情况 | 选择 | 理由 |
|---|---|---|
| 新产品线**要用现有底座**（账号 / 权限 / 后台 / 官网 / 支付…任意一项） | **MUST 进现有仓单根共享** | 底座能力在 `specs/` 只定义一次，各线的 change 引用它。各开各的仓，底座会被复制成 N 份然后各自漂移，跨线依赖只能靠人肉同步 |
| 新产品线**完全独立**，不碰任何现有能力 | **起独立仓**（用 openspec-kit 起） | 硬塞进单根只会让两批互不相干的需求互相干扰编号、评审、所有权 |

**判断方法**：把新产品线要用到的能力列出来，逐个问「现有仓的 `specs/` 里已经有了吗」。**有一个就算共用**——不要因为"我只用它的登录"就认为可以独立。

⚠️ **判错的代价不对称**：本该单根却起了独立仓 → 底座漂移，几个月后要做痛苦的合仓；本该独立却挤进单根 → 只是有点吵，随时可以拆出去。**拿不准时选单根。**

### 起了独立仓之后：跨仓依赖怎么走（未决）

一旦分成多个仓，`contracts/` 这套机制就**只在仓内有效**——它靠的是相对路径和同仓 R 号会签。

独立仓将来若要用到别的仓的能力（很常见：一开始说完全独立，半年后要接统一登录），现在**没有现成的走法**。已知的候选是 git submodule 引契约目录、或把契约发布成独立的小仓，各有代价，都还没验证过。

**在定下来之前**：独立仓要跨仓依赖时，MUST 先找体系 Owner 定走法，**MUST NOT 自己拷一份对方的契约文件进来**——那就是底座漂移的第一步。

## 一之二、单根共享的代价

选了单根，代价是**共享写入**——多人往同一个目录树里写。下面几节就是为了让这件事不出事。

---

## 二、目录所有权

| 路径 | 谁能写 | 说明 |
|---|---|---|
| `changes/NN-xxx/` | 该包 **Owner 独占** | 一包一 Owner，不共写 |
| `prototypes/NN-xxx/` | 跟包走 | 目录名与变更包同名 |
| `contracts/` | **供稿方**写，消费方只读 + 会签 | 见第三节 |
| `requirements.md` | 各 PM 只改**自己需求域**的行 | 见第五节 |
| `review-raw/` | 全局共用，谁开会谁丢 | 文件名带 R 号 + 日期，**只增不改不删** |
| `specs/` | **只由归档动作写** | 任何人不手改（review-convention 已定） |
| `references/` | 谁引用谁放 | 放进来就是共享资料，删除前先搜引用 |
| `conventions/` `assets/` `tools/` `config.yaml` `AGENTS.md` 拆包方案 | **体系 Owner** | 改动前在群里说一声——这些是所有人的地基 |

**判断自己能不能改某个文件**：它属于你 Owner 的变更包吗？不属于 → 找 Owner，别直接改。

---

## 三、跨人协作走契约，不互读 spec

**规则**：需要别人包里的东西时，**不要直接读对方的 `specs/*/spec.md`**。由对方（供稿方）在 `contracts/` 写一份契约，你只读契约。

**为什么**：

- spec 会随变更包**归档流转**——今天在 `changes/03-question-paper/specs/`，上线后就进了 `specs/` 或 `changes/archive/`。你的引用会断
- 直接互读等于把两个包**焊死**：对方改任何一条 Requirement 都可能悄悄破坏你的假设，而他不知道你在读
- 契约是**故意收窄的稳定接口**：只暴露对方需要的，其余实现细节可以自由改

**契约的义务**：

1. 供稿方在 `contracts/<契约名>.md` 写全接口的出入参形状、规则、边界与判断顺序
2. 契约与 Owner 包 `design.md` 里的对应条款（C1 / C4 …）**MUST 逐字一致**，Owner 包的 design 是正本，契约是对外副本
3. 契约改动 **MUST 双方会签**：双方各自的 `review-notes.md` 记一条，**引用同一个 R 号**，任一方未记即视为未生效
4. 消费方发现契约讲不清楚 → 提问，不要自行推断，更不要绕过契约去读对方 spec

**现有契约索引**（本仓每新增一份契约，在此登记一行）：

| 契约 | 正本（Owner 包的 design.md） | 对外副本 |
|---|---|---|
| _（尚无契约。示例：C1 登录态与权限 → `changes/01-xxx/design.md` → `contracts/登录态与权限契约.md`）_ | | |

## 四、冲突避免

git 产生冲突的唯一条件是**两个人改了同一个文件的同一行**。按第二节的所有权划分，绝大多数文件只有一个人写，冲突从源头就不存在。

只有两处需要额外约定：

**① `requirements.md`（唯一多人写的文件）**

- 按**需求域分段**，各改各段；不改同一行 → git 自动合并
- 真撞了：`git pull --rebase` 后把冲突段交给 AI 处理，它能看懂两边意图
- 新增需求点前先读下一节，**别急着开新域**

**② 变更包序号 NN**

- **全局连续**，跨产品线不重新计数
- 建包前 **MUST 先 `git pull`**，看清当前最大序号再 +1
- 两人同时建包撞号了：后 push 的那个改名（序号是包的身份，但还没人引用时改名代价最小；一旦被别的包引用就不许再改）

**③ 日常两个动作**

```bash
git pull      # 开工前
git push      # 收工后
```

漏 pull 的代价是基于旧状态干活；漏 push 的代价是别人看不到你的结论、还可能重复劳动。

## 五、需求域怎么建、需求点怎么编号

**共用一份 `requirements.md`，不是每人一份。** 因为需求域是按**能力**切的，不是按产品线切的——一个仓里通常有若干个域是多条产品线共用的底座（账号 / 权限 / 后台 / 官网这类）。

本仓现有的域清单见 `openspec/requirements.md` 开头的目录，每个域标注了「共享底座」还是「某产品线专属」。**新增域时 MUST 在那里补一行并标注归属。**

每人一份 requirements 的后果是：共享底座那几个域被复制成 N 份，然后各自漂移——这正是单根要避免的（第一节）。

### 5.1 新需求进来，按这四步判断

**第 1 步 · 先读，再动笔。** `git pull` 后通读现有全部域。跳过这步的代价是开出一个跟别人重叠的域，之后所有 spec、变更包、契约的引用都要返工。

**第 2 步 · 判归属。** 问一句：**这个需求会落到哪个已有系统上？**

| 落点 | 结论 |
|---|---|
| 任何一个**已有系统**（官网 / 后台 / 内容中心 / 码表…） | 进对应的**已有域**，哪怕它是别人在用的共享域 |
| 需要一整套全新的、别人碰不到的能力 | 开**新域** |
| 说不清 | **别猜，群里问**——归错域比晚半天贵得多 |

判归属看的是**能力落点**，不是「这是谁的需求」。同一条产品线的需求完全可以落在三个不同的域里。

**第 3 步 · 定编号。**

| 情况 | 怎么编 | 例 |
|---|---|---|
| 落在已有域 | 该域内递增 | 新增的内容管理需求 → `A5-8` |
| 新能力域 | 全局连续开新域，**不另起字母** | 已有 A1–A6 时下一个是 `A7`，不是 `B1` |
| 完全独立的新产品线（不共用任何底座） | 才用新字母 | `B1`、`C1` |

**为什么新域不另起字母**：字母代表「与现有体系完全不相干」。只要还共用底座里任何一样，就仍在 A 序列里——另起字母会让人误以为那是一套独立体系，从而重复定义底座。

> 走到「完全独立的新产品线」这一格时，先回第一节重新过一遍判据：真的完全独立的话，它多半不该待在这个仓里，而该用 openspec-kit 起一个自己的仓。

**第 4 步 · 该打招呼就打招呼。**

- 往**共享域**加需求点 → 群里说一声，让该域相关 Owner 知道
- **开新域** → 群里说一声，顺带确认没人已经在开同一个

**都不是审批，是通知。** 目的是避免两条线对同一能力提出互斥要求，拖到开发阶段才发现。

### 5.2 这套判据同样适用于变更包与契约

同一个问题在三个地方会重复出现，判据是同一条——**看能力落点，不看谁提的需求**：

| 对象 | 共享的处理 | 专属的处理 |
|---|---|---|
| 需求域 | 进已有共享域 | 开新域 |
| 变更包 | 底座能力由**一个包**统一改（如 Admin 归 `01-admin-foundation`），别的线引用 | 各线开自己的包 |
| 能力 spec | `specs/<能力>/` 只定义一次 | — |
| 跨线依赖 | 走 `contracts/` 契约，不互读 spec（第三节） | — |

**反模式**：为了「自己的线自己管」而把共享能力复制一份。复制的两份三个月后必然不一致，而且没人知道哪份是对的。

### 5.3 什么时候拆文件、怎么拆

**默认不拆。** 单文件的好处是跨域依赖（`前置依赖` 列引用别的域编号）一眼可查，且 `config.yaml` 只需声明一个事实源。

**出现下面任一情况才拆**：

- 域数量超过 10 个
- 单文件超过 400 KB（AI 每次读全量会明显变慢）
- 同一周内出现两次以上 `requirements.md` 的合并冲突

**拆的维度：按归属拆，不按产品线拆。**

```
requirements.md            索引表 + 共享底座域
requirements-<线>.md        该线专属域
```

理由同 5.2：共享域按产品线拆就会被复制成 N 份。

**拆分是一次性动作，MUST 一次做完这五件事**，缺任何一件都会留下断链：

1. 建新文件，把整域**移**过去（不是复制，原文件里删干净）
2. `requirements.md` 顶部加索引表：域号 / 名称 / 所在文件 / 归属（共享 or 哪条线）
3. `config.yaml` 的「需求事实源」改为逐文件声明，写明每个文件装哪些域
4. 改 `openspec/tools/bind-full-view.py` —— 它写死了按 `openspec_root/requirements.md` 找需求清单
5. 全仓搜 `requirements.md`，把指向已迁走域的引用改到新文件（`grep -rn "requirements.md" openspec/`）

**谁来拆**：体系 Owner。拆分动的是所有人的地基，不是某条线能单独决定的。

## 六、Gitee 权限：所有人都是开发者

本仓是**私有仓**，没被加成员的人连 clone 都不行。加人时 **一律给「开发者」**，包括还在培训、还没跑通流程的新同事。

**为什么不给新人「观察者」**：Gitee 的观察者**不能 push**，而上手流程的最后一步就是 push。卡在那里的人只会以为工具坏了。练习包是他本人的目录，误伤范围有限，真改错了第七节的兜底就够。

| Gitee 角色 | 能做 | 不能做 |
|---|---|---|
| 观察者 | clone / pull、提 Issue 与 PR | **push** |
| **开发者**（都给这个） | push 到非保护分支 | 改仓库设置、管理成员 |
| 管理员 | 改设置、加人 | — |

管理员怎么加人见 `docs/git-setup.md` 文末「管理员侧」。

## 七、误改了别人的文件怎么办

git 不阻止任何人改任何文件，这是刻意的——**加锁的代价远大于偶尔改错**。真出事的兜底是：

1. `git log -- <文件路径>` 查谁在什么时候改了什么
2. `git show <commit>` 看具体改动
3. `git checkout <commit>^ -- <文件路径>` 还原到改动前

**任何版本都在历史里，改错不会丢东西**。发现被误改，直接找对方说一声，不用走流程。

> 对比：如果用「单向同步覆盖」而不是 git，同事的改动会被静默抹掉、不留痕迹。git 不是冲突的来源，它是丢文件的解药。

## 八、不做的事（避免过度设计）

- **不上分支保护 / PR 流程**：3–5 人的产品团队，目录所有权 + git 可追溯已经够。等到出现「同一文件多人高频争抢」再说
- **不给每人开独立分支**：需求文档不是代码，长期分支只会让所有人看不到彼此的最新结论
- **不做目录权限锁**：Gitee 的权限粒度是仓级，做不了目录级；靠规范 + 可追溯

---

## 九、纳入流程的机制

- 本规范已由 `openspec/config.yaml` 的 context 声明，所有会话自动遵守
- 新同事上手见仓库根 `QUICKSTART.md`，第 3 步会读到本规范
- 与另两份规范的分工：**评审**走 `review-convention.md`，**发布**走 `publish-convention.md`，**协作边界**走本文件
