# 发布与共享规范（渲染物分发）

> 定位原则一句话：**git 是事实源（给开发和 AI 消费），团队服务器是渲染物分发（给人看、给人下载）。服务器上的一切都是快照，以仓库为准。**
> 本仓 `openspec/config.yaml` 已声明遵循本规范。

## 一、发布时机（挂进流程的三个钩子）

| 时机 | 发布什么 | 给谁 |
|---|---|---|
| **评审前**（评审闭环第 1 步） | 评审包：导航页 + 评审原型 + openspec 文档 + zip | 评审与会者（会议通知附 URL） |
| **签字后 / 开发中变更（R2+）执行后** | 覆盖更新同一发布包（spec 定稿版） | 研发——未进 git 协作前的需求包快照 |
| **归档后**（可选） | 账本渲染页 | 全团队 |

## 二、发布包结构

```
团队服务器/<成员目录>/<change-name>/     ← 变更包英文名作目录
├── index.html                          ← 导航页：原型入口 + 文档清单 + zip 下载按钮 + 发布时间与轮次（R 号）
├── prototypes/*.html                   ← 评审原型，浏览器直接看
├── openspec/…                          ← MD 原样目录（可逐个浏览，浏览器显示纯文本属正常）
└── <change-name>-openspec.zip          ← 全套 MD 打包；开发下载解压后整目录喂给 Cursor / Claude Code
```

## 三、命名与路径规则

1. 外层目录与文件名**全英文**（防 URL 乱码）；中文源目录由 AI 做英文暂存副本后上传
2. zip 内部文件名同样保持英文（防 Windows 解压乱码）
3. **同一变更包始终覆盖同一路径**——URL 恒定，会议通知里的旧链接永远指向最新版；index.html 上标注发布时间与评审轮次（R 号）供辨识

> 上传走团队上传 skill（`tencent-lighthouse-team-upload`，公司服务器）；不要与个人腾讯云服务器混用。

## 四、操作（一句话触发）

PM 说：

> 发布 <change-name> 评审包

AI 执行：建英文暂存副本 → 生成 index.html → 打 zip → 团队上传服务上传 → **URL 回写变更包 review-notes.md 头部**（发布记录行：轮次 / 时间 / URL）→ 回报链接。

## 五、全景装订视图（解决"需求被拆散"）

源文件保持拆分（AI 消费、防腐化），**完整的单页文档以"生成的渲染视图"形式存在**：

- 工具：`openspec/tools/bind-full-view.py <变更包目录>` → 生成变更包内 `full-view.html`（工具随首个变更包发布时落地）
- 内容：需求清单 + proposal + design（mermaid 图直接渲染）+ 全部能力域 spec + tasks，单页装订、左侧目录导航、头部标注状态与生成时间
- **评审决议不装订**：决议最终结果已同步进 proposal/design/spec，装订即冗余；追溯"为什么"查 review-notes 源文件（头部状态标记仍从它提取）
- 触发语：**「装订 &lt;变更包&gt; 全景文档」**
- 时机：评审前随评审包发布；每轮 R 决议执行后、签字后**重新装订覆盖**
- 铁律：full-view.html 是生成物，**勿手改**——它和源文件不一致时，永远以源文件为准、重新装订解决

## 六、约束

- 签字后 spec 再有变更（开发中变更 R2+），执行完变更**必须重新发布覆盖**——服务器快照与仓库不同步超过一轮即视为事故
- 开发正式在 git 仓库协作后，zip 通道降级为评审专用，研发一律读仓库 `openspec/`
- 归档后发布包保留并在 index 标注「已归档」，或按需下线
