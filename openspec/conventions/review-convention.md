# 评审决议规范（变更包的第五张纸）

> 目的：打通「团队评审」与「OpenSpec 变更包」之间的断层。评审产生的每条决议必须落进变更包、驱动 spec/原型更新、并留痕可追溯。本规范对所有需求变更包生效。
> 本仓 `openspec/config.yaml` 已声明遵循本规范。

## 一、目录约定

一次评审产出四件东西：**proposal / 原型 / spec / tasks**。但它们**不都放在 change 目录里**——工具管辖的 change 目录只装 schema 认的 artifact，原型与评审进件另有其位：

```
openspec/
├── changes/NN-<变更名>/       ← 变更包：只装 schema 定义的 artifact + 本包决议账
│                                 目录名带序号（NN-kebab-case），序号即包名的一部分，见 README 第二节
│   ├── proposal.md
│   ├── design.md / tasks.md / specs/
│   └── review-notes.md        ← 第五张纸：本包的正式决议账（执行依据，AI 维护）
├── review-raw/                ← 评审进件口，全局共用（PM 随手丢，原样留存）
│   └── R1-2026-07-15-meeting.md（任意格式：md / docx / xlsx / 图片）
├── prototypes/NN-<变更名>/*.html ← 评审原型，独立于 change 包；目录与文件名同变更包名
│   └── archive/NN-<变更名>/   ← 随 change 归档时移到这里
├── assets/<kit 名>/           ← 跨包共享的原型底座（主题 / 外壳 / 模板 / 注入脚本）
└── tools/                     ← 生成器与校验脚本
```

**为什么 review-raw 全局、review-notes 留包内**——两者性质不同，别一起搬：

| | 性质 | 归属 | 理由 |
|---|---|---|---|
| `review-raw/` | PM 的进件口，原始材料 | **全局** | **一场评审会通常同时过多个 change**，产出的是一份记录。逼 PM 先想清楚"这场会属于哪个包"才能落笔，与「随手丢」的设计意图相悖；勉强归档到某一个包，另几个包就丢了线索 |
| `review-notes.md` | 该包的正式决议账 | **包内** | 头部状态行就是该 change 的状态标志（评审中/已签字）；决议按包拆解后各归各家，才能随包归档、随包追溯 |

分工：**`review-raw/` 是 PM 的进件口（随手丢、全局一处），`review-notes.md` 是 AI 提炼后的正式账（按包拆解、规整可查）。**

**R 轮次全局连续编号**：R 号是「第几轮评审」，一场会一个 R 号，可同时涉及多个 change。各包的 `review-notes.md` 用同一个 R 号开节，靠它对上同一场会的原始记录。

**原始记录须在头部声明涉及哪些包**（原来靠所在目录隐含，全局后必须显式）：

```markdown
# R4 原始记录 · 2026-08-05
涉及变更包：01-admin-foundation、02-content-taxonomy
渠道：线下评审会（与会：产品/教研/研发）
```

**归档**：`review-raw/` **不随 change 归档** —— 它是按时间排的会议流水，一份记录可能横跨多个包，某个包归档不该带走它。`review-notes.md` 随包归档。

**原型为什么独立于 change 包**——两条硬依据，不是偏好：

1. OpenSpec 的 `spec-driven` schema **只定义 4 个 artifact**（`proposal` / `specs` / `design` / `tasks`），`prototypes` 不在其内。塞进 change 目录属于往工具管辖的目录里掺私货。
2. `publish-convention` 的发布包结构本就是 `prototypes/` 与 `openspec/` **并列**。仓库里同构，发布时不必再搬。

「四张纸（proposal / 原型 / spec / tasks）」这句说的是**产出物有四件**，不是目录归属——别把它读成「原型放 change 目录里」。

**代价与对策**：`openspec archive` 只搬 `changes/<变更名>/`，**不会带走原型**。故归档时 MUST 同步把 `prototypes/<变更名>/` 移到 `prototypes/archive/<变更名>/`，否则留下孤儿。索引脚本会把找不到对应变更包的原型标为「⚠ 无对应变更包」，作为兜底提醒。

**共享底座另放**：主题 / 外壳 / 模板 / 注入脚本放 `assets/<kit 名>/`（如后台线的 `assets/admin-kit/`）——多个变更包共用，塞进任一包都是错位。

原型 MUST 自包含（样式脚本内联，无外部请求），双击即可打开——研发与评审者不需要装任何东西。

**跨包浏览用索引**：

```bash
openspec/tools/build-prototypes-index.mjs      # 生成 openspec/prototypes-index.html
```

列出变更包名、原型标题、section 清单、评审状态、更新时间；点变更包名开整份，点 section 名直达该页，已归档的置灰。**索引是生成物，新增或改动原型后重跑即可**，不手维护。


## 二、review-notes.md 格式

文件头一行状态标记（这就是变更包的状态流转标志）：

```markdown
# Review Notes: <变更名>
状态：评审中 ｜ 已签字（R2 · 2026-07-20）   ← 二选一，AI 更新

## R1 · 2026-07-15 · 评审会（与会：产品/教研/研发）
### 1. <决议短标题>
- 定位：room-booking · A1-3 取消预订二次确认
- 结论：任何失败对用户统一提示「兑换码无效」，具体原因仅上报埋点
- 原因：不向用户暴露运营节奏（码的启停/次数）
- 落点：redemption spec「兑换校验」+ 原型 兑换页-01 旁注   ← AI 执行后回填

### 2. …（一条决议一节；被推翻的旧设计注明"推翻 R0 初稿"）
```

规则：
- 一轮评审一个 R 节，只增不改（R2 推翻 R1 的，在 R2 里写明，R1 保留）
- 记**结论**不记讨论过程；每条必有定位与原因
- proposal 里的「评审待定项」每条都必须在某个 R 节里出现拍板结果
- 「落点」由 AI 执行改动后回填，作为决议 → 文件的追溯链；凡改动了需求内容的决议，落点 MUST 同时含需求事实源的 A 编号与 spec 路径（见第四节）

## 三、完整闭环（七步）

| 步 | 动作 | 谁 |
|---|---|---|
| 1 会前 | AI 发布评审包到团队服务器（见 publish-convention.md），议程 = 原型 URL + proposal 待定项清单 | AI 备好，PM 发会 |
| 2 会中 | 按三要素记录：定位 / 结论 / 原因 | PM（任意格式） |
| 3 会后 | 原始记录丢进 `openspec/review-raw/`（全局一处，头部写明涉及哪些包），一句话通知 AI | PM |
| 4 提炼 | AI 提炼成决议清单，含糊处反问，PM 确认 | AI ↔ PM |
| 5 执行 | AI **先回写需求事实源（见第四节）**，再同步更新 spec / 原型旁注 / proposal（清待定项），写入 review-notes R 节并回填落点 | AI |
| 6 验收 | AI 输出对照表（决议 → 落点 → 状态），PM 逐行核对 | PM |
| 7 签字 | PM 回复确认 → AI 将状态改为「已签字（Rn）」→ 变更包进入待施工 | AI |

通知 AI 的标准一句话：

> 评审记录在 `openspec/review-raw/R1-xxx.md`，按评审决议规范提炼并更新相关变更包

## 四、回写需求事实源（强制）

> 变更包不是需求的终点。需求事实源是 `config.yaml` 声明的需求列表（`openspec/requirements.md`）。
> **评审决议只落进变更包、不回写列表，事实源就会过时**——之后任何人（含 AI）读列表都会读到已被推翻的旧需求，并据此推导出错误的 spec。

**三个触发条件，命中任一即须回写：**

1. **proposal「评审待定项」有了结论** —— 结论若确定或改变了需求内容（如某个字段的字符数上限、某清单的具体条目、某状态的流转规则），须写进对应 A 条目，并删掉列表里的「待定」「TBD」字样。
2. **review-raw 的决议要求改需求** —— 评审推翻或修订了原需求（如删除某个状态、改变某条规则、调整字段），须直接改对应 A 条目，而不是只改 spec 了事。
3. **画原型过程中产生的需求补充或变更** —— 原型是需求的照妖镜，画的过程必然撞出需求没写清的地方（缺页面要素、缺后续态、流程有断点）。这些补充与变更 MUST 同样回写，**不能只活在原型里**。

**回写的目的地是两处，缺一不可：**

| 目的地 | 写什么 |
|---|---|
| 需求列表的 A 条目 | 产品语言的完整描述，供同事独立阅读 |
| 变更包的 `specs/*/spec.md` | 可判真伪的 Requirement 与 Scenario，供开发实现与验收 |

**只写需求列表、不写 spec 是最常见的疏漏**——spec 才是开发的实现与验收依据，漏了等于该规则不会被测到。实例：某轮定了「停用账号须二次确认」「重置密码不展示新密码」，回写了需求列表却漏了 spec，直到复查才发现。**两处都要改，改完两处都要复查。**

**回写规则：**

- 回写目标 = 需求列表的对应 A 条目；一条决议牵动多个 A 条目的，逐条改全，不留半改状态。
- 列表与 spec 的**措辞可以不同**（列表是产品语言，spec 是可判真伪的规格），但**结论必须一致**，不允许一处已改、一处未改。
- 回写后在 review-notes 的「落点」里同时列出 A 编号与 spec 路径，例如：
  `落点：A1-2 会议主题字数上限 + room-booking spec「主题 40 字符硬截断」+ design C1`
- **需求列表 MUST 自包含**——即便同事与你在同一个仓里，也不能靠「让他去读我的 spec」补全。三条子规则：
  - **规则性内容**（清单、枚举、取值表、状态机结论）MUST 写全在 A 条目正文里，宁可与 spec 重复录入。
  - **大块参考资料**（字段字典、状态机图、数据文件）MUST 放 `openspec/references/`，用**相对路径**引用（如 `references/booking-state-machine.png`、`references/meeting-rooms.json`）。
  - MUST NOT 用「详见某个 spec」代替规则本身，MUST NOT 指向仅内网可访问的 URL。确需保留在线链接的，MUST 括号标明「在线原型，不在仓内」，且其关键结论仍须以文字写进正文。
  - **降低耦合优先于消除重复**——重复的代价是两处同步，指针的代价是别人根本读不懂。
- **不必回写**的仅限：读需求的人用不上的纯技术实现选型（库表结构、框架/中间件选型、接口协议、内部实现的推导过程）。判据是「另一位 PM 不打开你的 spec，能不能独立看懂这条需求」，而不是「这条算不算需求」。<br>反例：枚举的字面值表看似实现细节，但同事要据此打标与联调，故 MUST 全表写进需求条目，不可只留指针。

> **自包含的判据**：不是「离线包能否独立开工」，而是「同事不读你的 spec，能不能读懂这条需求」。跨人协作的边界见 `collaboration-convention.md`。

**顺序：先列表，后变更包。** 先回写事实源，再改 spec / design / tasks，最后回填落点。反过来做（先改 spec 再倒推列表）容易造成两边漂移，且丢失「需求为什么变」的因果。

**自检**：每轮评审执行完，回答一句——「本轮有哪几条决议改了需求？对应的 A 编号都改了吗？」答不上来即视为未闭环。

## 五、字段的「取代」MUST 当轮删除

**新增一个字段去「取代」旧字段时，MUST 在同一轮把旧字段删掉。** 只写「X 取代 Y」而把 Y 留在字段表里，不是过渡期，是**当场造出第二个事实源**——下游实现二选一，选哪个都合法，从此静默漂移。

判据一句话：**「取代」是删除动作，不是描述动作。** 写下这两个字，本轮就必须有对应的字段删除落点。

**本仓已经踩过两次，都在同一个变更包内：**

| 轮次 | 声明 | 实际发生 |
|---|---|---|
| R11 | `blanks[].pinyin`「**取代**原『拼音提示』」 | `prompt` 没删。此后 02 骨架拿 `prompt` 装拼音、03 示例当它不存在、`qbRender` 只读 `prompt` 不读 `pinyin`、老师端连录入入口都没有——四处互不相容，到 R33 才发现 |
| 早期 | 排序题答案「可多解」写进 `body.acceptedOrders` | 信封 `answer` 里那份单解拷贝没删。两份答案没有任何规则说明判分读哪个，原型只能录一解，规格与实现分叉了三轮 |

两次的病因完全相同：**加了新的、声明了取代、没删旧的。**

**执行清单**（本轮内做完，缺一即视为未闭环）：

1. 旧字段从**全部** spec 的字段表 / 结构表里删除——不是标注「已废弃」，是删掉
2. 全部 JSON 示例 / 骨架同步改用新字段，**包括 `references/` 下给外部消费方的副本**
3. 需求列表对应 A 条目同改（回写规则见第四节）
4. 原型的录入表单与渲染逻辑同改——**渲染器读旧字段是最容易漏的一处**，它不在 spec 里、`validate` 查不出来
5. 跨包消费方（如考生端）受影响的，写进会签清单当作**接口变更**逐条确认
6. 全仓 grep 一次旧字段名，确认剩余命中只是「已删除」的说明性文字

### 5.1 需要打「唯一例外」的归类，多半是归错了（R34 补）

**判据一句话：一条通则如果不得不为某个字段写「唯一例外」，先怀疑这个字段根本不属于这条通则。**

**本仓的案例（R33 → R34）**：R11 立了「配套拼音」通则——每个中文文本字段可一键生成拼音、非必填、供辅助显示。R33 把填空题的**空位提示**并了进去，随即被迫为它打三条例外：必填、不可被拼音开关隐藏、是题面内容不是辅助显示。**三条例外，等于把通则的每一条都否掉了**——这已经不是例外，是另一个东西。

漏掉的追问是「**这两个字段注的是同一类对象吗**」：配套拼音注的是**一段既定文本**（按字对齐，文本几个字就几段），空位上**根本没有文本**，它提示的是「该往里填什么」。对象不同，规则自然对不上。

代价不止是文档别扭——归错类会**沿着错误的类比长出错误的数据形状**：`pinyin` 跟着答案的「;」分隔写法被写成 `wán;wánchéng`，与答案数组一一对应，而一个空位只能显示一句提示，渲染端无从取舍。这个 bug 从 R33 一直带到 R34 才被 PM 一句「每个空的提示从哪输入」问出来。

**执行清单**：

1. 写下「唯一例外 / 特例 / 除…外」时，**停一次**，问「例外项与通则项是同一类对象吗」
2. 例外条款超过 1 条，**默认判定为归错类**，拆成独立字段 + 独立 Requirement
3. 拆出来的字段 **MUST 改名**——沿用旧名（如 `pinyin`）会让消费方按旧类的隐含契约去用它（可隐藏、可送 TTS、必然是拼音）
4. 通则那一侧 MUST 同步**删掉例外条款**，而不是留着「见 X Requirement」的转指

---

**确需保留旧字段的**（如存量数据迁移期），MUST 在 spec 里写明**保留到哪一轮、由谁在什么条件下删**，并明确「读取时以哪个为准」——没有这三样，就不算过渡期，只算漏删。

## 六、纳入流程的机制

- 本规范已由 `openspec/config.yaml` 的 context 声明，处理变更包评审的会话自动遵守。
- 落地到真实开发仓库时，在项目 CLAUDE.md 加一行：「需求变更包的评审决议遵循 openspec/conventions/review-convention.md（第五张纸）」。
- 示例参照：首个 change 归档后，在此补一份真实的 review-notes.md 示例链接。
