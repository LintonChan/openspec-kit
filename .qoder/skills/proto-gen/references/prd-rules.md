# PRD bullets 写法规范

> **适用范围**：设备无关。PC · macOS / Mobile 系列共用同一套 PRD 写法。

## 面板两种模式：先选对，再动笔

panel 里装什么，取决于这份原型给谁、干嘛用，有两种模式，**开工前先定**：

| 模式 | panel 装什么 | 何时用 | 事实源关系 |
|---|---|---|---|
| **产品语言改写型**（本文档主体） | 手写产品语言 bullets（讲功能逻辑） | 无 spec 依据、或纯构思/草稿阶段的原型 | 原型即最新表达 |
| **评审型**（见文末专章） | **注入 spec 真身**（Requirement + Scenario 逐字，脚本回填） | 有 OpenSpec 变更包、要「评审原型顺带把 spec 评审掉」 | **spec 是唯一事实源**，panel 从 spec.md 现抽 |

**判据**：这份原型背后有没有 change 包的 `specs/*/spec.md`？有且评审目标是 spec → **走评审型**，不要手写改写 bullets（改写=有损转写，评审改写版 ≠ 评审 spec）。没有 → 走改写型，按下文规范手写。

下文除文末「评审型」专章外，均为**改写型**的写法规范。

---

每个 section 的 PRD bullets 按**从上到下视觉布局顺序**排列，顶部控件 → 主区内容 → 操作按钮 → 弹窗/抽屉。

## 铁律：以功能为导向，不是描述 UI

PRD 旁注要讲**这个功能背后的实际逻辑**，不是复述界面上肉眼可见的东西。

**来源**：逐条从需求与 spec 里取，而不是看着图现编。有 openspec 变更包时，`specs/*/spec.md` 的 Requirement 与 Scenario、`design.md` 的决策与约束，就是 PRD 的原料。**每条 bullet 都应能指回某条需求或 spec**。

**要覆盖的五个维度**（缺哪个，开发就在哪个上盲打）：

| 维度 | 该写什么 |
|---|---|
| 业务 | 这个功能解决什么、为什么这样定、有什么代价 |
| 功能 | 有哪些操作、各自的前置条件与后果 |
| 产品 | 字段/列/入口的取舍理由，为什么没有某个功能 |
| 数据 | 字段含义、存什么、来源、唯一性、是否可变 |
| 交互 | 状态流转、禁用与拦截规则、异常与失败处理 |

**目标**：拿着原型能直接给开发评审——他照着能实现，不用回头猜需求。

写这些（有价值）：

- 触发条件、前置校验（「删除前须先解绑全部账号，否则拦截」）
- 禁用/置灰的规则与原因（「超管行操作全置灰——超管不可被降权」）
- 字段的业务含义（「绑定账号数 —— 供删除前的解绑校验用」）
- 该操作对应哪个权限键、谁能做
- 为什么这样设计（「建角色与配权限分两步，新建角色默认不含任何权限」）

不写这些（无价值）：

- 控件尺寸、间距、颜色（「查询控件统一 240px 宽」）
- 元素排布（「按钮与搜索框同一行」）
- 组件外观（「表头白底灰字」）

**判据**：这条信息，评审者盯着原型图看能不能自己看出来？能看出来的就别写——**UI 机制肉眼可见，写了是噪音**；看不出来的（规则、条件、原因）才是 PRD 该承载的。

**例外**：若某个 UI 形态是框架强制且反直觉（如「确定在左、取消在右」），在需求文档里**全局写一次**即可，不在每页 PRD 重复。

## 铁律：一条 bullet 只讲一个要点

PRD 面板宽仅 360px，长句在这里会挤成一大团，评审时没人读得下去。**能拆就拆，宁可多几条短的，也不要一条长的。**

具体要求：

- **一条 bullet = 一个要点**。出现「，同时…」「；此外…」「。这是因为…」就该断开成两条
- **单条控制在 ~30 字以内**，超了先想能不能拆，拆不动再留长
- **并列项逐条列**，不要塞进一句里用顿号连接
- **「结论 + 依据」拆成两条**：先给结论，再单独一条给依据/原因
- 禁止把多个句号连成一段话塞进一个 `<li>`

对照：

```
✗ 差：首列为多选框（宽 55px），各列居中；表头白底灰字（非灰底），行 hover 底色 #f5f7fa。

✓ 好：
  - 首列为多选框，宽 55px；各列居中
  - **表头白底灰字**（非灰底）
  - 行 hover 底色 `#f5f7fa`
```

## 元素描述模板

每条 bullet **以加粗元素名作标题前缀**（`<strong>元素名</strong>：` / md 里 `**元素名**：`），冒号后接「展示...」描述：

| 元素类型 | 描述模板 |
|------|------|
| 静态文本/标题 | `**{元素名}**：展示「{文案}」{位置/样式}` |
| 内容卡片/列表 | `**{元素名}**：展示 {元素}，内容来源：{数据源}` |
| 按钮 | `**{按钮名}**：展示「{文案}」按钮（{样式}），点击后{行为}` |
| 链接 | `**{链接名}**：展示「{文案}」链接，点击后跳转至 {目标}` |
| 状态指示 | `**{状态名}**：展示 {状态元素}（{文案/颜色}），用于 {含义}` |
| 交互（hover/focus） | `**{交互名}**：{触发行为}时{反馈}` |
| 条件分支 | `**{元素名}**：{条件 A}时{元素状态描述}；{条件 B}时{元素另一状态描述}` |

规则：

- 每条单一职责，一个可感知元素一条
- **加粗标题前缀**：以 `**元素名**：`（HTML 面板 `<strong>元素名</strong>：`）起头，元素名取简短可感知的控件/区域名（如「登录按钮」「积分余额」「套餐卡片」），冒号后接「展示...」描述
- 描述含"是什么"和"什么数据/什么行为"两维
- 数据来源用通俗描述（来自配置 / 来自后端 / 静态 / 由用户输入），不写实现细节
- 冒号使用全角 `：`

### 条件分支型描述

同一控件在不同上下文有不同行为时，用**条件对照**清晰列出每种分支，避免歧义。

示例：

> - **删除图标·默认渠道**：渲染为禁用态（灰色 + not-allowed 光标 + 透明 hover 背景），tooltip 文案为「默认渠道不可删除」；点击无任何响应
> - **删除图标·非默认渠道**：使用危险色样式，用于强调破坏性操作

写法要点：

- 每个分支独立一条 bullet（不要在同一行用「如果…则…」并列描述）
- 条件前缀简短（如「默认渠道」「失败态」「未登录用户」），冒号后描述视觉/行为
- 用于同控件不同态、同元素不同用户身份、同字段在不同流程的差异

## 重复内容处理

同一模块内多个 section 共享相同结构时，只在**第一个 section 完整描述**，后续 section 改用引用，降低维护成本。

### 四类常见重复场景

| 场景 | 示例 | 引用写法 |
|------|------|---------|
| **外壳级通用模块**（顶部窗口栏 / 侧边栏 / 顶部工具栏）在同模块所有 section 重复出现 | 页面-01 / 页面-02 / 页面-03（同 app-shell 套同一套外壳） | 第一个 section 完整描述这些通用模块；**后续 section 一律省略，不写「与首页保持一致」之类废话引用**，只列主区差异；除非外壳本身有差异（如某 tab 隐藏侧栏某项）才单独写一行差异说明 |
| **详情页多状态变体**（同模板、不同主按钮/badge） | 详情页-01 / 详情页-02 / 详情页-03（不同状态） | `详情页通用结构（返回链接、图标 + 名称 + 副标题、完整简介、操作按钮）同 详情页-01` |
| **弹窗通用结构**（遮罩 + X 关闭按钮）在同模块多处弹窗 | 弹窗-01 / 弹窗-02（不同弹窗） | `遮罩、X 关闭按钮同 弹窗-01；底层为 页面-01 dimmed 态` |
| **遮罩在同文件连续出现**（抽屉/弹窗叠加） | 弹窗-02 → 弹窗-03 | `遮罩同上；[本节独有内容]` |

> **外壳级模块的特殊性**：与详情页 / 弹窗 / 遮罩三类「内容级」重复不同，外壳（顶部窗口栏 / 侧边栏 / 顶部工具栏）是**整个应用共用**的，写 1 次足够。后续 section 写「侧边栏与首页一致」这种引用句本身就是赘述——直接删，**留白即默认外壳无变化**。只有当外壳真的变了（如某侧栏列表保留上次缓存这种差异），才独立写一条 bullet 说差异。

### 引用规则

1. 第一个引入该结构的 section 必须完整描述，它是后续 section 的锚点
2. 后续 section 先写一行引用，再列差异点（用「差异：」或直接列差异 bullets）
3. 差异内容仍按正常描述模板写，不省略
4. 若两个弹窗内容差异较大，不强制引用，完整描述更清晰

### 正面案例

「编辑」/「编辑-默认」/「删除」三个 section 的引用式差异描述典范：

- 「编辑」完整描述编辑子页结构
- 「编辑-默认」首行 `结构与「编辑」一致，差异点见下`，之后只列差异（默认项额外的 badge、只读字段、恢复按钮等）
- 「删除」首行 `底层背景为「编辑」子页内容...`，复用底层描述，重点写弹窗本身

## 改动型原型：功能概览只写本次改动

当原型是给**既有页面**新增 / 修改功能的迭代切片（而非全新页面）时，功能概览**只描述本次改动引入或改变的元素**，既有功能一律不复述。

- ❌ 反例：给某详情页新增一个配置区，却把返回入口、状态徽标、主操作按钮、依赖列表、删除区等既有元素全列一遍 —— 冗余
- ✅ 正例：只写新增的配置区及其中的开关 / 入口卡片；既有头部、列表、操作区一概不写
- **判断标准**：这条 bullet 描述的元素，是本次改动**新增或改变**的吗？不是 → 删
- 全新页面原型不受此约束（所有元素都是「本次」，照常从上到下枚举）
- section 标题可点明改动主题（如「XX 页 · 新增 XX 区」），让读者一眼知道本切片只讲增量

## PRD 写作风格（人类视角，不写代码语言）

PRD 旁注的读者是 **产品 / 测试 / 研发**——三类都是人。写法要保证 3 个角色都能 0 上下文读懂：

### 1. 用产品语言，禁止代码语言

| ❌ 反例 | ✅ 正例 |
|---|---|
| `sidebar-brand 用 .brand-mark + h2.brand-name 渲染` | 左侧导航栏品牌区：顶部展示品牌 logo + 文字 |
| `AgentStatusBadge variant=success` | 卡片右上角展示绿色「已安装」徽标 |
| `onClick → router.push('/detail/:id')` | 点击后前往对应详情页 |
| `installedCount > 0 ? showBadge : null` | 当任一数字为 0 时该项徽标自动隐藏，让顶栏保持简洁 |

### 2. 系统级元素描述要平台无关

涉及操作系统、浏览器、设备等会变的元素，描述用「跟随...呈现」「按...而定」「原型图仅展示 X 风格作示意」，不要写死具体形态：

- ❌ 「窗口栏左上展示红黄绿三个圆点（关闭/最小化/最大化）」
- ✅ 「窗口边框跟随用户当前操作系统呈现，原型图仅展示 macOS 风格作示意」

### 3. 品牌/视觉细节不写括号注释

正式 logo 待定时不要在 PRD 写「（紫色方形 logo + 文字）」之类装饰描述。原型用什么视觉是另一回事，PRD 描述的是「有 logo + 有文字」这件事本身。

### 4. 关键交互独立成 bullet

不要把交互塞在状态描述末尾，分行写明确：

- ✅ 独立 bullet：「**「进入」按钮**：符合条件的卡片底部均为圆形「进入」按钮，点击后前往对应详情页（说明 / 操作项等）」

### 5. 失败 / 异常处理独立成 bullet

不要让失败处理塞在「状态流转」末尾。toast 文案、列表保留逻辑、错误后的可恢复路径**单独一条 bullet**：

- ✅「**安装失败处理**：安装失败时弹出 toast 提示「{对象名称} 安装失败，请重试」；任务队列保留该失败任务记录，用户可在任务队列中查看错误详情或重新触发安装」

### 6. 不写「整体视觉」「整体氛围」这类废话 bullet

「浅灰桌面背景 + 圆角窗口 + 投影」属于原型视觉而非产品需求。删。

### 7. 版本号 / 数量等数据展示规则要枚举所有分支

数据格式因状态而异时，逐个状态列出：

- ✅「**版本号展示规则**：已安装的项显示当前已装版本（如 v1.0.45）；**可升级**的项同时展示「当前版本 → 可升级版本」（如 v0.10.0 → v0.11.0）；未安装 / 安装中 / 检测中的项显示「最新版本：vXX」」

## md 与 HTML 面板同步

功能概览内容同时存在于 `.md` 文件和 HTML `prd-panel` `<li>` 中，修改时两处必须同步更新。

HTML 面板结构：

```html
<div class="prd-section">
  <div class="prd-section__title">{编号}：{页面短名}</div>
  <ul>
    <li><strong>元素名</strong>：展示 ...（从对应 md 抄）</li>
  </ul>
</div>
```

每个 section 对应一个 `prd-section`，只装该 section 的 bullets，不混入其他 section。

## 评审型：面板注入 spec 真身

> 仅用于「有 OpenSpec 变更包、评审目标是 spec」的原型。不手写改写 bullets，panel 由 `assets/spec-inject.mjs` 从 `specs/*/spec.md` **逐字回填** Requirement + Scenario。目标：**走完所有 section = 逐字看完所有 Requirement/Scenario，评审原型即评审 spec**。

### 面板结构：锚点 + 注入槽

改写型的手写 `<ul>` 换成「`data-req` 锚点 + 一对 spec 注入标记」，脚本回填标记之间：

```html
<div class="prd-section" data-req="knowledge-tree#知识点 ID 由系统按规则生成、只读、永久稳定">
  <div class="prd-section__title">知识点 ID 规则</div>
  <!-- @proto-gen:spec:start -->
  <!-- 脚本按 data-req 注入 spec 真身，勿手改 -->
  <!-- @proto-gen:spec:end -->
</div>
```

- `prd-section__title` 仍保留，作**人读的 section 短名**；spec 真身注入其下
- 注入内容 = 该 Requirement 陈述句 + 其下**全部** Scenario 逐字（`.spec-req` / `.spec-scenario`，样式在 `shared.css`）

### 锚点 data-req 写法

格式 `<cap>#<Requirement 标题>`：

| 部分 | 取值 | 说明 |
|---|---|---|
| `cap` | `specs/` 下的能力目录名 | 如 `knowledge-tree`、`question-type-registry`（小写 kebab） |
| `Requirement 标题` | `### Requirement:` 后整句 | **逐字复制**，含空格；标题变了锚点即失效（审计会抓） |

规则：

- **锚点打在 Requirement 层，不细到 Scenario**——挂一条 Requirement 自动带出它名下全部 Scenario，覆盖率在 Requirement 层查全即等于每条 Scenario 都被看到
- **一个 section 挂多条**：空格分隔（`data-req="cap#标题A cap#标题B"`；标题内空格不受影响，因标题绝不含 `#`）
- **可选 hover 联动**：锚点后加 `@<组件key>`（`cap#标题@qtstruct`），注入块带 `data-target`，hover 该需求高亮对应原型组件（Requirement↔组件级）。不写则无联动，不影响评审
- **多对多正常**：一条 Requirement 可被多个 section 挂、一个 section 可挂多条，覆盖率只要求「全覆盖」，不要求一一对应

### 切片：一条需求罗列 N 种并列情形时

有的 Requirement 正文是**一串并列情形**（如「各结构题型 JSON 示例」下 7 个题型各一份），而每屏原型只对应其中**一种**。整条注入 = 每个录入页都糊上 7 份 JSON，评审者要自己从噪音里找那一份。

此时锚点加 `§<切片标签>`：

```
question-bank#各结构题型 JSON 示例（录入参考）§判断题@jopt
```

- **切片边界** = 正文里以 `**小标题**` 领起的段，到下一个 `**小标题**` 为止
- **preamble**（首个 `**小标题**` 之前的总述）与**全部 Scenario** 永远保留——切的是并列项，不是需求本身
- 标签**前缀匹配**：`§判断题` 命中 `**判断题**（看图判断 · HSK1 听力）`
- 面板标题后自动标「**切片 · 判断题**」，评审者一眼知道这不是需求全文
- 顺序固定：`cap#标题§切片@组件key`

**切片完整性审计**：一条 Requirement 若只以切片形式出现（没有任何 section 整条挂它），脚本会检查它的**每个切片都被挂到**——漏一个就报错。否则「走完所有 section = 逐字看完这条需求」的承诺会破。

**判据**：这条 Requirement 的正文，本屏是不是只用得上其中一段？是 → 切片；整条都是本屏的规则 → 别切。

### 回填与双审计（交付前必跑）

```bash
~/.claude/skills/proto-gen/assets/spec-inject.mjs {原型.html} --change {变更包目录}
```

- **一致性**：注入即从 spec.md 现抽，结构上不走样；CI/交付前用 `--check` 比对，面板与 spec 不同步则报错
- **死锚点**：`data-req` 指向 spec 不存在的 Requirement → 报错
- **覆盖率**：spec.md 每条 Requirement 是否都被 ≥1 section 挂到；漏的报错。确属无 UI 的规则，写进 `{变更包}/spec-coverage-ignore.txt`（一行一个 `cap#标题`）豁免

**两审计全绿才算可交付**——这是「评审原型 = 评审完整 spec」的硬保证。

### spec 改了怎么办

只重跑 `spec-inject.mjs`，**不动原型**。panel 永远是 spec.md 的现抽投影，原型迭代（改 UI）与需求变更（改 spec）各自独立。
